## 1. System Classification

**System Type:** Structured LLM Decision Engine

**Description:**
Four AI players (GPT-4o, Gemini, Claude, Llama 3) make sequential poker decisions at every action point in a Texas Hold'em game. Each decision is a single LiteLLM acompletion() call: a structured prompt containing hand math (hand strength, pot odds, win probability), available actions, archetype description, and table state → fenced JSON response (action + reasoning) → parse + validate → play or fall back to deterministic archetype logic. Reasoning text streams token-by-token to viewers via `event: reasoning` SSE events. "Good" means: valid JSON action every time, archetype-legible play style differences visible to non-poker-expert viewers, and reasoning text that reads like a real player thinking aloud — regardless of whether the LLM call succeeded or fell back.

**Critical Failure Modes:**
1. **Game halt on LLM failure** — a timeout, malformed response, or provider error causes the game to stall indefinitely. Must never happen: fallback must engage within the 8s global deadline.
2. **Invalid action played** — LLM returns an action not in `valid_actions()` (e.g., raise above all-in limit, check when there's a bet), corrupting chip state. Must be caught and overridden by fallback.
3. **Archetype indistinguishability** — all four players behave identically across a session; Gunslinger and Rock look the same to viewers. Defeats the core viewer experience.
4. **Cost runaway** — a provider outage or loop causes repeated retries or token blowout with no circuit breaker, burning API budget on a session no one is watching.
5. **Reasoning stream corruption** — SSE reasoning events arrive out of order, duplicated, or attributed to wrong player, breaking the viewer's "AI thinking" experience.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Entertainment / AI Spectator Sports

**User Population:** Anonymous viewers watching a live AI poker game in a browser — non-poker-experts who want to see AI "personalities" clash and understand why each AI made its move.

**Stakes Level:** Medium

**Output Consequence:** LLM decision output is acted on directly as a poker game action (fold / call / raise with amount). Malformed or invalid output corrupts game state. Reasoning text is shown verbatim to viewers — poor output degrades viewer experience and believability.

### What Domain Experts Evaluate Against

**Dimension: Archetype voice consistency**
- Good: Reasoning text uses language and reasoning patterns that match the assigned archetype without being prompted — the Gunslinger talks about aggression and pressure, the Rock explains why the hand isn't worth the risk, the Chaotic Optimist just believes it's gonna work out.
- Bad: All four players use identical phrasing or sentence structure regardless of archetype; a viewer cannot tell which player is which from reasoning text alone.
- Stakes: Critical
- Source: LLM persona research (PersonaGym, EMNLP 2025) — language style consistency is the primary measurable axis of persona fidelity; without it, character differentiation collapses entirely.

**Dimension: Action-archetype coherence**
- Good: The action taken (fold/call/raise) is plausible given the archetype's documented bias parameters — the Gunslinger raises when pot odds are marginal, the Rock folds when win probability is below its threshold. A viewer who has watched 3 hands can predict roughly what each player will do next.
- Bad: A Rock shoves all-in with a weak hand; a Gunslinger folds to a min-bet. Action contradicts the persona so sharply that viewers lose trust in the characters.
- Stakes: Critical
- Source: AI-06 (REQUIREMENTS.md) — "differences must be legible to non-poker-expert viewers"; PokerBench research (arxiv 2501.08328) confirms LLMs default to exploitative play patterns that override persona instructions unless explicitly constrained.

**Dimension: Reasoning naturalness (no fourth-wall breaks)**
- Good: Reasoning text reads like a player thinking aloud at the table — "I've got top pair but this board is wet, I need to protect it," or "I don't care, I'm shoving." First-person, present-tense, emotionally plausible.
- Bad: Reasoning sounds like an AI debug log or system prompt echo — "As an AI language model playing the Gunslinger archetype, I will now evaluate the pot odds..." or output is raw JSON fields leaked into the reasoning string.
- Stakes: High
- Source: Virtual AI streamer research (ScienceDirect 2025) — "behavioral realism" (natural language and emotional expression) is the key determinant of viewer engagement and perceived anthropomorphism; system-prompt leakage is the most common observed failure mode in deployed AI persona products.

**Dimension: Fallback invisibility**
- Good: When the LLM times out, the fallback notice ("acting on instinct") appears in the ReasoningPanel and the game continues without interruption. Viewers see a brief character-consistent message, not an error state.
- Bad: The game stalls visibly (spinner, frozen UI, missed action) or the fallback notice reads like a technical error ("LLM call failed: timeout after 2000ms"). Viewers perceive a broken product rather than a character quirk.
- Stakes: Critical
- Source: D-12 (04-CONTEXT.md) — fallback format specified; viewer experience requires the seam to be invisible; game halt is listed as Critical Failure Mode 1 in Section 1.

**Dimension: Valid action output rate**
- Good: Every hand, every player plays a valid action (one of the options in `valid_actions()` with a legal amount). The game progresses without chip-state corruption across a full session.
- Bad: Any hand where the LLM returns a raise amount above the all-in limit, a check when facing a bet, or an action string not matching the enum — even if caught by fallback, it signals prompt or parsing fragility that will worsen at scale.
- Stakes: Critical
- Source: AI-04 (REQUIREMENTS.md) — validation is a hard requirement; PokerBench (arxiv 2501.08328) documents that LLMs "hallucinate drawing possibilities" and misread available actions, making explicit validation non-optional.

### Known Failure Modes in This Domain

1. **Archetype collapse under pressure** — When hand strength is extreme (very strong or very weak), all LLMs converge on the same "obvious" action regardless of persona. A Gunslinger with the nuts and a Rock with the nuts both raise — archetype differentiation evaporates at the extremes. Poker experts identify this immediately; non-experts lose engagement when all four players start looking identical.

2. **Reasoning text persona bleed** — LLMs that have been trained to be helpful, harmless assistants resist playing aggressive or "tilted" characters. The Gunslinger softens its aggression; the Chaotic Optimist hedges its reasoning with qualifiers. Research (arxiv 2511.04962) documents fidelity scores dropping from 3.21 for moral archetypes to 2.61 for antagonistic ones — directly affecting the most entertaining characters.

3. **System prompt leakage into reasoning** — The LLM echoes portions of its system prompt (archetype description, instruction text, JSON format instructions) into the `reasoning` field. Viewers see raw prompt text verbatim, which completely breaks character immersion. Particularly common with smaller models (Llama 3) that have weaker instruction-following.

4. **Poker-invalid reasoning that is narratively plausible** — The LLM produces reasoning text that sounds authentic ("I have a flush draw, I'm semi-bluffing") but the actual hand contains no flush draw. Experienced poker viewers catch this immediately and lose confidence in the AI's "intelligence." The reasoning is disconnected from the actual math context that was provided in the prompt.

## 2. Framework Decision

**Selected Framework:** LiteLLM direct (`acompletion`) — no higher-level agent framework

**Version:** `>=1.83.0` (already installed — pinned in pyproject.toml from Phase 1)

**Rationale:**
LiteLLM is already the established abstraction layer from Phase 1. Phase 4's integration point is a sequential async decision loop: one `acompletion()` call per player per turn, with `asyncio.wait_for()` for the 2s per-call timeout and an `async for chunk in stream` iterator for reasoning token streaming. Every higher-level framework (LangChain, LangGraph, CrewAI) wraps this exact pattern without adding anything the bespoke fallback, circuit breaker, and JSON parser cannot handle directly. The fallback logic, archetype bias parameters, budget tracking, and per-provider circuit breaker are all custom business logic that no framework replaces — they must be written regardless. Adding a framework layer is strictly net-negative: more dependencies, more abstraction to debug, no new capability for a linear sequential loop.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|-----------------|
| LangChain | Adds PromptTemplate + chain abstraction over what is already a direct call pattern; useful if prompt complexity grows significantly, but premature for Phase 4 scope |
| LangGraph | Graph/node overhead for a linear `for player in turn_order` loop; massive overkill; no stateful checkpoint needed (game state lives in the engine) |
| CrewAI | Role/task/crew model doesn't map to "one async acompletion() call per player per turn"; wrong abstraction shape entirely |
| OpenAI Agents SDK | Vendor lock-in to OpenAI; project uses 4 providers including Llama 3 (self-hosted); incompatible with multi-provider requirement |
| Claude Agent SDK | Claude-only; project must remain model-agnostic across all 4 providers |

**Vendor Lock-In Accepted:** No — LiteLLM is the provider-agnostic abstraction; any OpenAI-compatible model can be swapped in via config

from litellm.exceptions import APITimeoutError, APIError, RateLimitError

# Regex: extracts the JSON object from a ```json ... ``` fenced block
_JSON_FENCE_RE = re.compile(r"```json\s*(\{.*?\})\s*```", re.DOTALL)

INDIVIDUAL_TIMEOUT_S = 2.0


async def llm_poker_decision(
    model: str,           # e.g. "openai/gpt-5-nano"  — from models.config.json
    system_prompt: str,   # player identity + archetype persona (stable)
    user_prompt: str,     # hand state + math context (changes every call)
) -> dict | None:
    """
    Returns parsed dict {"action": str, "amount": int, "reasoning": str}
    or None on any failure — caller engages deterministic fallback.
    Streams tokens; this example collects full text (production version
    publishes each delta to SSE via publish_reasoning()).
    """
    try:
        # Double-layer timeout: asyncio.wait_for (hard wall) + timeout= (HTTP cleanup)
        stream = await asyncio.wait_for(
            acompletion(
                model=model,
                messages=[
                    {"role": "system", "content": system_prompt},
                    {"role": "user",   "content": user_prompt},
                ],
                stream=True,
                max_tokens=300,    # hard cap — prevents token blowout (INFRA-05)
                temperature=0.7,
                timeout=INDIVIDUAL_TIMEOUT_S,
            ),
            timeout=INDIVIDUAL_TIMEOUT_S,
        )
    except (asyncio.TimeoutError, APITimeoutError, RateLimitError, APIError) as exc:
        logging.warning("LiteLLM call failed for %s: %s", model, exc)
        return None

    # Iterate stream — delta content is None on first (role) and last (finish) chunks
    full_text = ""
    async for chunk in stream:
        delta = chunk.choices[0].delta.content
        if delta:                          # guard: None on non-content chunks
            full_text += delta
            # In production: await publish_reasoning(redis, player_id, phase, delta, done=False)

    # Signal end of stream to SSE clients
    # In production: await publish_reasoning(redis, player_id, phase, "", done=True)

    # Extract and parse the fenced JSON block
    match = _JSON_FENCE_RE.search(full_text)
    if not match:
        logging.warning("No fenced JSON block from %s. raw[:200]=%r", model, full_text[:200])
        return None

    try:
        return json.loads(match.group(1))
    except json.JSONDecodeError as exc:
        logging.warning("JSON parse error from %s: %s", model, exc)
        return None

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `acompletion()` | Async coroutine wrapping any provider's chat completion API; returns an async stream when `stream=True` | Every LLM decision call — the single entry point for all 4 providers regardless of vendor |
| `asyncio.wait_for()` | Standard library wrapper that raises `asyncio.TimeoutError` after N seconds | Wrap every `acompletion()` call to enforce the 2s per-call hard deadline (D-11) |
| `chunk.choices[0].delta.content` | Incremental text token in each streamed chunk; `None` on non-content chunks (role announcement, finish signal) | Inside `async for chunk in stream` — always gate with `if delta:` before using |
| `litellm.exceptions.*` | Provider-agnostic exception hierarchy: LiteLLM maps all provider HTTP errors to these types | Catch `APITimeoutError`, `RateLimitError`, `APIError`, `BadRequestError` uniformly — no provider-specific handling |
| LiteLLM model strings | Format `"provider/model-name"` — e.g. `"openai/gpt-5-nano"`, `"gemini/gemini-3.1-flash-lite-preview"`, `"deepseek/deepseek-v4-flash"`, `"xai/grok-4"` | Passed as the `model` parameter; loaded exclusively from `models.config.json` at runtime |

### Common Pitfalls

1. **`asyncio.wait_for()` does not cancel the underlying HTTP connection.** When the outer timeout fires, `acompletion()` is cancelled at the coroutine level but the provider's TCP socket may remain open, wasting file descriptors under concurrent load. Fix: pass `timeout=INDIVIDUAL_TIMEOUT_S` directly to `acompletion()` as well — LiteLLM uses this to close the HTTP connection from its side. Use both layers: `asyncio.wait_for()` as the hard wall and `timeout=` on the call for HTTP cleanup.

2. **`chunk.choices[0].delta.content` is `None` on the first and last chunks.** The first chunk carries `role="assistant"` with `content=None`; the final chunk has `finish_reason="stop"` with `content=None`. Doing `full_text += delta` without the `if delta:` guard raises `TypeError: can only concatenate str (not "NoneType") to str`. Always write `if delta := chunk.choices[0].delta.content:`.

3. **Model string prefix determines provider routing — casing and prefix are not optional.** `"gpt-5-nano"` and `"openai/gpt-5-nano"` may route differently. A missing prefix can cause silent misrouting or a `NotFoundError`. Load model strings exclusively from `models.config.json`; never hardcode them in `decision.py` or pass them as unqualified names.

4. **`asyncio.wait_for()` with `stream=True` can fire mid-stream.** If a model begins streaming but takes >2s to complete, `wait_for` fires after the stream object has been returned. At that point `full_text` is partial and the fenced JSON block is incomplete — regex extraction will fail. This is correct behaviour: discard the partial buffer and engage fallback. Do not attempt to use or parse a partial stream response.

5. **`num_retries` is silently ignored when `stream=True`.** LiteLLM's built-in retry mechanism cannot wrap a streaming response because the `acompletion()` coroutine returns before the stream is consumed. Passing `num_retries=3` with `stream=True` has no effect and creates a false sense of retry safety. All retry/fallback logic must be implemented at the call site — in the circuit breaker in `budget.py`.

### Core Pattern

Full decision loop with streaming SSE publish, timeout, circuit breaker, Pydantic validation, and fallback:

```python
# backend/app/ai/decision.py
import asyncio, re, json, logging
from litellm import acompletion
from litellm.exceptions import APITimeoutError, RateLimitError, APIError, BadRequestError

from app.ai.archetypes import Archetype
from app.ai.models import LLMDecisionResponse, ReasoningEntry
from app.ai.prompt import build_system_prompt, build_user_prompt
from app.ai.budget import BudgetTracker, CircuitBreaker
from app.broadcast.publisher import publish_reasoning
from app.engine.models import Player, GameState, Action, ActionType

_JSON_FENCE_RE = re.compile(r"```json\s*(\{.*?\})\s*```", re.DOTALL)
INDIVIDUAL_TIMEOUT_S = 2.0


async def llm_decision_fn(
    player: Player,
    archetype: Archetype,
    game_state: GameState,
    math_ctx: dict,          # {win_probability, pot_odds, hand_strength} from poker_math.py
    valid_acts: list[dict],  # from valid_actions(player, game_state)
    redis_client,
    budget: BudgetTracker,
    circuit: CircuitBreaker,
) -> Action:
    """
    DecisionFn implementation. Returns a valid Action — never raises.
    Falls back to deterministic archetype logic on any failure.
    """
    # Circuit breaker: skip LLM if provider has tripped (D-16)
    if circuit.is_open(player.litellm_model):
        return await _fallback_action(
            player, archetype, valid_acts, math_ctx,
            reason="circuit open", redis_client=redis_client, game_state=game_state,
        )

    system_msg = {"role": "system", "content": build_system_prompt(player, archetype)}
    user_msg   = {"role": "user",   "content": build_user_prompt(game_state, math_ctx, valid_acts)}

    raw_text = ""
    try:
        stream = await asyncio.wait_for(
            acompletion(
                model=player.litellm_model,
                messages=[system_msg, user_msg],
                stream=True,
                max_tokens=300,
                temperature=0.7,
                timeout=INDIVIDUAL_TIMEOUT_S,
            ),
            timeout=INDIVIDUAL_TIMEOUT_S,
        )

        # Publish each token as a reasoning delta event (D-01, D-02)
        async for chunk in stream:
            if delta := chunk.choices[0].delta.content:
                raw_text += delta
                await publish_reasoning(
                    redis_client,
                    player_id=player.id,
                    phase=game_state.phase,
                    delta=delta,
                    done=False,
                )

        # Signal stream complete to SSE clients
        await publish_reasoning(
            redis_client, player_id=player.id,
            phase=game_state.phase, delta="", done=True,
        )
        circuit.record_success(player.litellm_model)

    except (asyncio.TimeoutError, APITimeoutError) as exc:
        logging.warning("[%s] LLM timeout: %s", player.name, exc)
        circuit.record_error(player.litellm_model)
        return await _fallback_action(
            player, archetype, valid_acts, math_ctx,
            reason="timed out", redis_client=redis_client, game_state=game_state,
        )

    except (RateLimitError, APIError, BadRequestError) as exc:
        logging.warning("[%s] LLM error (%s): %s", player.name, type(exc).__name__, exc)
        circuit.record_error(player.litellm_model)
        return await _fallback_action(
            player, archetype, valid_acts, math_ctx,
            reason=type(exc).__name__, redis_client=redis_client, game_state=game_state,
        )

    # Parse and validate response
    parsed = _parse_response(raw_text, player.name)
    if parsed is None:
        return await _fallback_action(
            player, archetype, valid_acts, math_ctx,
            reason="parse error", redis_client=redis_client, game_state=game_state,
        )

    # Validate action is in valid_actions() (AI-04)
    valid_types = {a["type"] for a in valid_acts}
    if parsed.action not in valid_types:
        logging.warning("[%s] Invalid action '%s' not in %s", player.name, parsed.action, valid_types)
        return await _fallback_action(
            player, archetype, valid_acts, math_ctx,
            reason="invalid action", redis_client=redis_client, game_state=game_state,
        )

    # Approximate token budget tracking (D-15)
    prompt_tokens = len(system_msg["content"] + user_msg["content"]) // 4
    completion_tokens = len(raw_text) // 4
    budget.record(player.litellm_model, prompt_tokens, completion_tokens)

    return Action(type=ActionType(parsed.action), amount=parsed.amount)


def _parse_response(raw_text: str, player_name: str) -> LLMDecisionResponse | None:
    """Extract fenced JSON block and validate with Pydantic. Returns None on any failure."""
    from pydantic import ValidationError
    match = _JSON_FENCE_RE.search(raw_text)
    if not match:
        logging.warning("[%s] No fenced JSON block. raw[:200]=%r", player_name, raw_text[:200])
        return None
    try:
        data = json.loads(match.group(1))
    except json.JSONDecodeError as exc:
        logging.warning("[%s] JSONDecodeError at pos %d: %s", player_name, exc.pos, exc.msg)
        return None
    try:
        return LLMDecisionResponse.model_validate(data)
    except ValidationError as exc:
        for err in exc.errors():
            logging.warning("[%s] ValidationError field=%s msg=%s value=%r",
                            player_name, err["loc"], err["msg"], err.get("input"))
        return None


async def _fallback_action(
    player, archetype, valid_acts, math_ctx, reason: str,
    redis_client=None, game_state=None,
) -> Action:
    """
    Deterministic decision based on hand strength + archetype bias (D-11).
    Publishes a single fallback notice to the ReasoningPanel (D-12).
    """
    win_prob = math_ctx.get("win_probability", 0.5)

    if win_prob >= archetype.raise_freq and _has("raise", valid_acts):
        action = Action(type=ActionType.RAISE, amount=_min_raise(valid_acts))
    elif win_prob >= archetype.hand_looseness and _has("call", valid_acts):
        action = Action(type=ActionType.CALL, amount=_call_amount(valid_acts))
    elif _has("check", valid_acts):
        action = Action(type=ActionType.CHECK, amount=0)
    else:
        action = Action(type=ActionType.FOLD, amount=0)

    # Publish fallback notice — character-consistent, never a technical error message (D-12)
    if redis_client and game_state:
        notice = f"[{player.name} {reason} — acting on instinct]"
        await publish_reasoning(
            redis_client, player_id=player.id,
            phase=game_state.phase, delta=notice, done=True,
        )

    return action


def _has(action_type: str, valid_acts: list[dict]) -> bool:
    return any(a["type"] == action_type for a in valid_acts)

def _min_raise(valid_acts: list[dict]) -> int:
    acts = [a for a in valid_acts if a["type"] == "raise"]
    return acts[0].get("min_amount", 0) if acts else 0

def _call_amount(valid_acts: list[dict]) -> int:
    acts = [a for a in valid_acts if a["type"] == "call"]
    return acts[0].get("amount", 0) if acts else 0
```

### Tool Use

No external tools or function-calling. Structured output is embedded in the response body as a fenced JSON block and extracted with regex. This is intentional: it works across all four providers (OpenAI, Google, DeepSeek, xAI) without requiring `response_format={"type": "json_object"}` or tool-call support, neither of which is guaranteed on every provider-model combination.

### State Management

LLM calls are fully stateless. All context (hand state, archetype, math context) is rebuilt from `GameState` on every call. `GameState` is the single source of truth — it lives in the FastAPI engine and is never stored in or cached by the AI module. No cross-hand memory in v1 (deferred to v2 per CONTEXT.md).

### Context Window Strategy

Single-hand context only. Estimated prompt token budget per call:

| Segment | Approx Tokens |
|---------|--------------|
| System prompt (identity + archetype) | ~120 |
| User prompt (hand state + math + valid actions + opponents) | ~200 |
| Response (reasoning + fenced JSON block) | ~200 (capped at max_tokens=300) |
| **Total** | **~520 tokens** |

This is well within all four provider context limits (minimum: 8k on flash/nano-tier models). No truncation or summarization is needed at v1 scale. If the prompt must be trimmed, apply cuts in this order:
1. Shorten opponent summary to last action only (remove chip counts)
2. Abbreviate archetype guidance to one sentence
3. Abbreviate card notation (`Ah` → `A♥`)

Never remove: `win_probability`, `pot_odds`, available actions with amounts, current pot. These are the fields the model relies on to produce valid actions.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### 4b.1 Structured Outputs with Pydantic

LiteLLM does not provide a native Pydantic output parser. The pattern for this project: parse fenced JSON from response text → validate with Pydantic → return `None` and engage fallback on `ValidationError`. Do not use `response_format={"type": "json_object"}` — it is not universally supported across OpenAI, Google, DeepSeek, and xAI in the same call signature.

**Pydantic models (must match TypeScript interfaces in `app/_components/types.ts`):**

```python
# backend/app/ai/models.py
from pydantic import BaseModel, Field, field_validator
from typing import Literal


class LLMDecisionResponse(BaseModel):
    """Validated shape of LLM response — parsed from fenced JSON block in response text."""
    action: Literal["fold", "call", "raise", "check"]
    amount: int = Field(default=0, ge=0)
    reasoning: str = Field(min_length=1, max_length=500)

    @field_validator("reasoning")
    @classmethod
    def strip_reasoning(cls, v: str) -> str:
        return v.strip()


class ReasoningEntry(BaseModel):
    """
    MUST exactly match TypeScript ReasoningEntry in app/_components/types.ts:
      id, playerId, text, phase, streaming, action, amount
    Serialise with model_dump(by_alias=True) for camelCase JSON over SSE.
    """
    id: str
    player_id: str = Field(alias="playerId")
    text: str
    phase: str
    streaming: bool
    action: Literal["fold", "call", "raise", "check"] | None = None
    amount: int = 0

    model_config = {"populate_by_name": True}
```

**Retry policy:** Do not retry the same streaming call on `ValidationError`. With `stream=True`, the response object is returned before the stream is consumed — retry semantics are undefined, and a second identical call would likely produce the same malformed output. Log all `ValidationError` field failures with full detail (field name, received value, error message) for prompt tuning. Surface failures as fallback notices to viewers — never expose raw LLM output or stack traces.

After sufficient logged failures reveal a systematic pattern (e.g., a specific provider consistently omitting `amount`), fix the prompt (add a more explicit format constraint) rather than adding code-side coercion. Code-side coercion masks prompt quality issues and creates silent divergence between what the LLM thinks and what the game plays.

### 4b.2 Async-First Design

`acompletion()` is a native coroutine — it must be awaited inside an `async def` function. The game loop is already async (FastAPI + `asyncio.Queue` fan-out from Phase 3), so `acompletion()` integrates without any event loop bridging.

**The one critical mistake: nesting `asyncio.run()` inside a running event loop.**

```python
# WRONG — raises RuntimeError: "This event loop is already running"
# (triggered if called from within a FastAPI endpoint or background task)
async def make_decision(...):
    result = asyncio.run(llm_decision_fn(...))   # DO NOT DO THIS

# CORRECT — await the coroutine directly; the event loop is already running
async def make_decision(...):
    result = await llm_decision_fn(...)
```

**Stream vs. await for this use case:**

| Mode | Behaviour | When to Use |
|------|-----------|-------------|
| `stream=True` + `async for` | Yields tokens as they arrive; first token ~200ms | This project — enables live reasoning SSE for viewers |
| `stream=False` + `await` | Blocks until full response; first usable text ~1-2s | Not used here — unacceptable latency for live viewer experience |

**`asyncio.wait_for()` scope with streaming:** The timeout applies to the initial `await acompletion(...)` coroutine (obtaining the stream object), not to the subsequent `async for` iteration. Once the stream object is returned, individual chunk iterations can still block. Mitigation: pass `timeout=` directly to `acompletion()` so LiteLLM enforces the deadline at the HTTP transport level across the full stream lifetime.

**Testing:** In pytest, use `pytest-asyncio` with `@pytest.mark.asyncio`. Never call `asyncio.run()` inside a test function that is itself async — it raises the same "event loop already running" error. Use `anyio` if the project ever moves to a mixed sync/async test suite.

### 4b.3 Prompt Engineering Discipline

**System vs. user message split (D-04):**

```
System message = stable identity — who the player is and how they behave
User message   = volatile context — current hand state, changes every call
```

Never put hand state in the system message. It prevents any potential prompt caching benefits and mixes concerns that have different change rates. Never put identity or archetype instruction in the user message — models weight system-role instructions differently and the archetype voice weakens.

**System prompt structure:**

```
You are {player_name}, an AI competing in a live-streamed poker game.
Your archetype is {archetype_name}: {archetype_description}
Behavioral guidance: {archetype_guidance}

RESPONSE FORMAT — follow exactly, no other text:
```json
{"action": "<fold|call|raise|check>", "amount": <integer_chips>, "reasoning": "<1-2 sentences in character>"}
```
```

**User prompt structure:**

```
Hand: {hole_cards}. Board: {community_cards or "none"}. Phase: {phase}.
Pot: {pot}. Your chips: {player_chips}.
Win probability: {win_probability:.0%}. Pot odds: {pot_odds:.0%}. Hand strength: {hand_strength:.2f}.
Available actions: {valid_actions_formatted}.
Opponents: {opponent_summary}.
```

**Few-shot examples:** Do not inline few-shot examples in v1. The explicit format instruction is sufficient, and examples add ~100 tokens to every call. If JSON compliance degrades in testing on a specific provider, add one example (matching the exact `valid_actions()` shape for the current phase) to the system message for that provider only. Do not add examples globally — it increases cost for all providers.

**`max_tokens` is mandatory in production.** An uncapped call to a verbose model (e.g., DeepSeek, Grok) can return 1,000+ tokens of reasoning text, burning 3-5x the expected budget on a single hand. `max_tokens=300` is sufficient: the fenced JSON block + 1-2 sentences of reasoning reliably fits within 200 tokens; 300 is a safety margin. Never omit this parameter.

### 4b.4 Context Window Management

At v1 scale (~520 tokens per call), context window overflow is not a risk. Apply defensive rules in the prompt builder:

**Token budget enforcement in `prompt.py`:**

```python
MAX_SYSTEM_TOKENS = 150   # identity + archetype + format instruction
MAX_USER_TOKENS   = 250   # hand state + math + actions + opponents
# Total input ~400; output capped at max_tokens=300; combined well under 700 tokens
```

If `build_user_prompt()` exceeds `MAX_USER_TOKENS`, trim in this order and log a warning:
1. Remove opponent chip counts — keep only last action per opponent
2. Shorten archetype guidance in system message to one sentence
3. Abbreviate card notation

Never trim: `win_probability`, `pot_odds`, `valid_actions`. These are the fields that prevent invalid-action outputs.

**Cross-hand context (deferred v2):** When opponent profiling is introduced, cap cross-hand history at 3 hands per opponent. Summarise as a single line: `"Rock: called 3, raised 0, folded 1 in last 3 hands."` Never pass raw hand histories — they grow unboundedly and will eventually exceed even large context windows.

**Budget tracker and circuit breaker** are implemented in `backend/app/ai/budget.py`:

```python
# backend/app/ai/budget.py
from dataclasses import dataclass, field
from collections import defaultdict
import logging


@dataclass
class BudgetTracker:
    """In-memory per-GameSession spend accumulator. Reset at session start (D-15)."""
    _spend: float = 0.0
    _tokens: dict = field(default_factory=lambda: defaultdict(int))

    # Approximate cost-per-output-token by provider prefix
    # Update from provider dashboards before each deployment
    _COST_PER_TOKEN: dict = field(default_factory=lambda: {
        "openai":   0.0000004,    # gpt-5-nano output tier
        "gemini":   0.00000004,   # flash-lite-preview output tier
        "deepseek": 0.00000028,   # v4-flash output tier
        "xai":      0.000001,     # conservative estimate — update when confirmed
    })

    def record(self, model: str, prompt_tokens: int, completion_tokens: int) -> None:
        provider = model.split("/")[0]
        rate = self._COST_PER_TOKEN.get(provider, 0.000001)
        self._spend += (prompt_tokens + completion_tokens) * rate
        self._tokens[provider] += prompt_tokens + completion_tokens

    @property
    def total_spend(self) -> float:
        return self._spend

    def summary(self) -> dict:
        return {"total_usd": round(self._spend, 6), "tokens_by_provider": dict(self._tokens)}


@dataclass
class CircuitBreaker:
    """Per-provider consecutive error counter. Resets on session start (D-16)."""
    threshold: int = 3
    _errors: dict = field(default_factory=lambda: defaultdict(int))
    _open: set = field(default_factory=set)

    def record_error(self, model: str) -> None:
        self._errors[model] += 1
        if self._errors[model] >= self.threshold:
            self._open.add(model)
            logging.error(
                "CircuitBreaker OPEN for %s after %d consecutive errors — "
                "fallback will engage for remainder of session",
                model, self.threshold,
            )

    def record_success(self, model: str) -> None:
        # Reset only on success — only consecutive errors trip the breaker
        self._errors[model] = 0

    def is_open(self, model: str) -> bool:
        return model in self._open
```

**Caching:** Do not implement semantic or exact-match caching. Every prompt is unique (different hole cards, board, pot, opponent actions). Cache hit rate would be <1% and adds infrastructure cost without meaningful savings. The cost control mechanisms are: `max_tokens=300`, flash/nano-tier models, 2s timeout preventing hung calls, and the circuit breaker preventing provider runaway.

## 6. Guardrails

### Online (Real-Time)

These run synchronously in the decision path on every call. Each adds latency — kept minimal.

| Guardrail | Trigger | Intervention | Latency Cost | Maps to Failure Mode |
|-----------|---------|--------------|--------------|----------------------|
| **Timeout hard wall** | `asyncio.wait_for()` fires after 2s per call; global 8s deadline across all 4 players in one decision phase | Engage `_fallback_action()` immediately; publish `[{player} timed out — acting on instinct]` ReasoningEntry; game continues | ~0ms (timeout is the delay ceiling itself) | Game halt on LLM failure |
| **Invalid action catch** | `parsed.action not in valid_types` — LLM returned an action string not in `valid_actions()` for this player's position | Discard LLM response entirely; engage `_fallback_action()` with `reason="invalid action"`; log warning with player name + returned action | ~0ms (dict lookup) | Invalid action played / chip state corruption |
| **Raise amount cap** | `parsed.action == "raise"` and `parsed.amount > player.chips` (all-in limit) | Clamp `parsed.amount` to `player.chips` and continue — do not fallback for an amount-only violation; log warning | ~0ms (comparison) | Invalid action played / chip state corruption |
| **Circuit breaker** | `CircuitBreaker.is_open(model)` returns `True` (3 consecutive provider errors this session) | Skip `acompletion()` call entirely; route directly to `_fallback_action()` with `reason="circuit open"`; no HTTP call made | ~0ms (set lookup) | Cost runaway |
| **Fenced JSON parse failure** | Regex finds no ```` ```json ... ``` ```` block in LLM response, or `json.loads()` raises `JSONDecodeError`, or `LLMDecisionResponse.model_validate()` raises `ValidationError` | Engage `_fallback_action()` with specific reason (`"parse error"` / `"validation error"`); log raw response first 200 chars | ~0ms (regex + dict parse) | Invalid action played |

All five guardrails are implemented inline in `decision.py`. No external service call. Total added latency per decision: negligible (sub-millisecond checks only).

### Offline (Flywheel)

Batch analysis run after each session ends (or nightly over accumulated session logs). Feeds prompt iteration and archetype tuning.

| Metric | What It Measures | Sampling Strategy | Action on Degradation |
|--------|-----------------|------------------|----------------------|
| **Fallback rate per provider** | Percentage of decisions per provider that triggered `_fallback_action()` for any reason (timeout, parse error, invalid action, circuit open). Target: < 10% per provider per session. | All decisions — logged at session end by `BudgetTracker.summary()` extension | Fallback rate > 20% for a provider: inspect raw response logs for that provider; likely prompt format regression or model update. Add provider-specific few-shot example to system prompt if parse failures dominate. |
| **Archetype raise rate delta** | Gunslinger raise rate minus Rock raise rate across the session. Target: > 20 percentage points. | All decisions — tallied from action log at session end | Delta < 10 pp: archetype collapse is occurring. Review system prompt archetype guidance for both; increase specificity of behavioral instruction. Particularly watch high-win-probability hands (> 0.85). |
| **Reasoning naturalness score** | LLM judge (GPT-4o) scores sampled `reasoning` entries 1-5 for "sounds like a real player." Target: session average ≥ 3.5. | 20% random sample of all `reasoning` entries per session; 100% sample of entries flagged by the online code check (contains `"as an AI"`, JSON syntax, or non-existent card claims) | Session average < 3.0: prompt engineering regression — review system prompt for leakage vectors; check if a model update changed instruction-following behavior. Score < 2.0 on any individual entry: immediate human review. |
| **Per-session spend vs. estimate** | Actual `BudgetTracker.total_spend` vs. expected range ($0.02–$0.10/session). Detects token blowout (verbose model, `max_tokens` misconfigured) or undercounting (tracker not wired). | Every session | Spend > $0.15/session: check `max_tokens=300` is being passed in every call; check if a model is ignoring the cap and streaming past it. Spend = $0.00: tracker not wired — fix before next session. |
| **Circuit breaker trip frequency** | How often `CircuitBreaker` trips per provider across sessions. Target: 0 trips/week under normal conditions. | Every session — logged at session end | Any trip: investigate provider error logs immediately (rate limit, API key expiry, model deprecation). Two trips in one day: rotate provider or switch fallback model. |

Each `acompletion()` call then emits a trace to Phoenix automatically: model name, latency, prompt tokens, completion tokens, full prompt text, full response text, success/failure. Available at `http://localhost:6006`.

**Key Metrics to Track** (5 metrics, each maps to a Phase 4 success criterion):

| Metric | Phoenix Display | SC Mapped | Target |
|--------|----------------|-----------|--------|
| **Decision latency p95** | Span duration histogram per model | SC-1 (every player called and returns) | p95 < 3s per decision; p99 < 8s |
| **Fallback rate** | Count of spans tagged `fallback=true` / total spans | SC-4 (game continues on failure) | < 10% per provider per session |
| **Token count per call** | `prompt_tokens` + `completion_tokens` histogram | SC-6 (spend tracked) | Output tokens < 300 (enforced by `max_tokens`); alert if any call > 350 |
| **Archetype raise rate delta** | Custom metric logged at session end: `gunslinger_raise_rate - rock_raise_rate` | SC-2 (archetype bias visible) | > 0.20 (20 pp) per session |
| **Session total spend (USD)** | Custom metric from `BudgetTracker.summary()` logged as a session-end event | SC-6 (circuit breaker + spend tracked) | < $0.10/session; alert > $0.15 |

**Alert Thresholds:**

| Condition | Threshold | Action |
|-----------|-----------|--------|
| Decision latency p95 > 5s | Sustained over 3 consecutive decisions | Check provider status page; verify `asyncio.wait_for()` is wrapping the call; verify both timeout layers are active |
| Fallback rate > 20% for any provider | Single session | Inspect raw response logs for that provider; likely prompt regression or model API change |
| Any `completion_tokens` > 350 | Single call | `max_tokens` parameter not being passed; find the call site and fix immediately |
| Archetype raise rate delta < 0.10 | Single session | Archetype collapse occurring; review system prompt behavioral guidance; increase Gunslinger aggression instruction specificity |
| Session spend > $0.15 | Single session | Token blowout or circuit breaker not wiring to fallback; audit `BudgetTracker.record()` call sites |
| Circuit breaker trips > 0 | Any trip | Investigate provider errors immediately; do not wait for next session |

**Smart Sampling Strategy:**

Human review is expensive — apply it where signal is strongest. All sampling decisions are signal-based, not random.

| Signal | Priority | Review Action |
|--------|----------|---------------|
| Any `reasoning` entry that triggers the online code guardrail (contains `"as an AI"`, JSON syntax, or non-existent card) | Immediate — 100% review | Flag for prompt fix; check if it's provider-specific or universal |
| Reasoning naturalness LLM judge score < 2.0 | Same session — review before next run | Read full prompt + response for that decision; identify leakage vector |
| Any decision where fallback engaged with `reason="invalid action"` | Next-day review | Log the exact invalid action and prompt that produced it; add to reference dataset as FAIL example |
| Sessions where circuit breaker tripped | Immediate — review within 1 hour | Provider health check; key rotation if `AuthenticationError` was the trigger |
| First 3 sessions after any prompt change | 100% Gunslinger + Rock reasoning review | Verify archetype voice still distinct; check naturalness score hasn't regressed |
| Routine production session (no signals) | 20% random sample of reasoning entries | Monthly archetype voice calibration; LLM judge rescoring against human labels |
